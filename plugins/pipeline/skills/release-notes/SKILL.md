Aggregate `changelog/<branch>.md` files into a single quarterly release-notes document for the people who deploy the release. The output is `releases/<quarter>.md`.

**Why this skill exists:** The release pipeline rolls out code automatically, but some tickets need manual steps (DB scripts, gateway routes, cache flushes, per-environment config, feature-flag toggles). Each ticket's per-ticket changelog already records these in its `## Manual Steps` section (written by `/pipeline:ship` Step 5b or `/pipeline:changelog`). This skill is the consumer side — it gathers all those sections for one release window into one file the deployer can work through linearly.

**Inputs:**
- `<quarter>` — required. Format `YYYY-QN`, e.g. `2026-Q2`. Used as the output filename and the title.
- `--since <git-ref>` — optional. Override the default "since last release" detection. E.g. `--since v2026.04.0` or `--since 0b6448f`.
- `--dry-run` — optional. Print the aggregated content to stdout without writing the file.

Throughout, `<main>` is the repo's default branch (`main` or `master` — check `git symbolic-ref --short refs/remotes/origin/HEAD`).

---

## Step 1 — Determine the changelog set

Decide which `changelog/<branch>.md` files belong to this release.

1. **Default (no `--since`):** find the most recent `releases/*.md` file (lexicographic max). Read its header — it records the git-ref (`**Range:** <ref>..HEAD`) where the previous release ended. Use that as the lower bound.
   - If no prior `releases/*.md` exists, fall back to "all files currently in `changelog/`" — first-time bootstrap.
2. **With `--since <ref>`:** use `<ref>` directly.
3. **Build the file list:**
   - Run `git log <since-ref>..<main> --diff-filter=A --name-only --format= -- changelog/` to list changelog files added in the range. Strip duplicates (a file added then renamed shows twice).
   - Filter: only `changelog/*.md` (not subdirectories).
   - If the resulting list is empty, print "No new changelogs since `<ref>`. Nothing to aggregate." and exit.

Record the upper-bound ref too — `git rev-parse HEAD` at the time of the run — so the next release knows where this one ended.

---

## Step 2 — Parse each changelog

For every file in the list, read the file and extract:

| Field | Source |
|---|---|
| `ticketId` | The `#NNNN` after `**Ticket:**` in the header |
| `type` | The token before ` · ` after the em-dash on the `**Ticket:**` line (e.g. `Improvement`, `Bug`, `Feature`, `Security`) |
| `module` | The token after ` · ` on the `**Ticket:**` line |
| `title` | Parse from branch name (the H1), the `<Description>` segment — convert PascalCase to space-separated words. Or: fall back to the H1 verbatim. |
| `summary` | The body of the `## Summary` section |
| `manualSteps` | The body of the `## Manual Steps` section. Empty string if the section is exactly `_None._` (after trimming). |

If a file is missing a required section, log a warning and skip — do not abort. Bad changelogs should not block the release.

---

## Step 3 — Group and order

1. **Modules with manual steps come first.** Group entries with non-empty `manualSteps` by `module`. Order modules as they are listed in `.claude/rules/branch-management.md` if the project defines a module list there; otherwise alphabetically, with the cross-cutting module (`Shared` or equivalent) last. Inside each module, order by ticket ID ascending.
2. **All tickets table** — separately, list every parsed ticket (with or without manual steps) sorted by ticket ID ascending, for the "All tickets" appendix.

---

## Step 4 — Write `releases/<quarter>.md`

If `releases/` does not exist, create it.

Format:

```markdown
# Release Notes — <quarter>

**Range:** `<since-ref>..<head-ref>`
**Generated:** <ISO date>
**Tickets total:** <N>
**Tickets with manual steps:** <M>

## Manual steps for this update

> The following steps must be performed when updating to this release — grouped by module. If this section is empty, no manual steps are needed.

### <Module A>

#### #<ticketId> — <title>

<verbatim manualSteps content from changelog>

[<more tickets in this module>]

### <Module B>
[...]

## All tickets in this release

| Ticket | Type | Module | Title |
|---|---|---|---|
| #<id> | <type> | <module> | <title> |
| ...

---

_Generated by `/pipeline:release-notes <quarter>`. Source: `changelog/*.md`. Do not edit manually — re-run the skill to update._
```

If `branch-management.md` defines a work-item URL pattern, render the ticket cell as a link (`[#<id>](<url>)`).

When `--dry-run` is set, print the content to stdout instead of writing the file. Otherwise write `releases/<quarter>.md` (overwrites if exists — re-runs are idempotent).

---

## Step 5 — Final report

Print a one-line summary:

```
✓ Wrote releases/<quarter>.md — <N> tickets, <M> with manual steps. Range <since>..<head>.
```

If any changelog file failed to parse, list the offenders below the summary so the user can fix them.

## Notes

- **Don't archive consumed changelogs.** Leave `changelog/*.md` files in place after release. They stay as historical record. Future `/pipeline:release-notes` runs use the git-range filter (`<since>..<main>`) to skip them, so they don't get re-included. The cost is a permanently growing `changelog/` directory; the benefit is auditability and re-runnability of any past release.
- **Re-run idempotency.** Re-running `/pipeline:release-notes 2026-Q2` regenerates the same file. Running it after a few more tickets ship since the same `<since-ref>` produces an updated file with the new tickets included. The git ref bounds make this deterministic.
- **Pairing with a tracker flag.** If the project's tracker has a "manual steps required" boolean on the work item, it is a fast filter ("which tickets in this release have manual steps?"). This release-notes file is the *content* — the actual instructions. Both are populated from the same `## Manual Steps` section in the changelog, so they cannot drift.
- **Customer-facing wording.** When these notes feed customer communication, mark each feature clearly as either **automatically active after the update** or **opt-in / configurable**. An empty `## Manual Steps` section (`_None._`) does **not** mean "automatically active" — config-driven features are still off until an administrator enables them. When in doubt, ask the implementing developer before claiming "automatically available".
